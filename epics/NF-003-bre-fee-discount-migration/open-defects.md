**This is a snapshot.** Every line number here is dated and much of the code is

repo, then open the site. Do not plan off a line number without reading it.

## How to use this file

Each item has a stable ID. Take them one at a time and record the outcome in the
**Status** column — leave `open`, or set `fixed <date>`, `wontfix <reason>`,
`spec'd <repo>/specs/NNN-slug`.

Tags:

- **C** — confirmed: the researching agent read the code that proves it.
- **S** — suspected: inferred, needs a second look before it drives work.
- **live** — reachable in a default-config deployment today.
- **latent** — real code, but gated off by a flag or unreached by any caller.

Nothing here is a fix proposal. Several items have more than one defensible fix
and the choice is a design decision, not a cleanup.

## Sequencing

Recommended order, and why:

1. **§A security** — independent of the BRE migration and exploitable now.
   Does not need D4, G1 or G2 to close. Strong candidate for its own sub-epic.
2. **§C audit-durability composite** (E3 + E15 + E16) — also migration-independent,
   and it degrades the evidence you would need to reconstruct any past charge.
   The longer it runs, the more history is unexplainable.
3. **E1 / F1 / F2** — resolution and currency/rounding parity. These belong inside
   NF-003 proper: they sit on the `resolve_published_ruleset` vs `collapse_and_pin`
   parity surface already recorded in `epic.md` money-correctness item 4, and any
   fee/discount work built on top of them inherits the divergence.
4. Everything else, by plane.

### Composite: the audit trail for a charged fee is not durable

**E3 + E15 + E16 + E14 together**, which no single-repo view surfaces:

1. The ledger row can be **rewritten** by any later retrieve (E3).
2. Its pointer to the evaluation log can be **stale** (E16).
3. The evaluation log itself is **eligible for deletion**, because `reference` is
   never sent (E15 + E14).

The money charged is not at risk. The ability to reconstruct *why* that amount
was charged is. Treat these four as one work item, not four.

### The silent-zero family

Distinct triggers, one invisible outcome — a zero or wrong fee with no error
anywhere in the stack. Worth fixing as a class, because a guard added at only one
trigger leaves the rest:

| Trigger | Ref |
|---|---|
| Subscription's ruleset mapping deactivated / deleted | `epic.md` item 6 |
| Ruleset UUID dangling at a deleted or unpublished ruleset | E4 |
| No ruleset matches at all | E8 |
| OrderView-scoped rule keyed on an unpopulated NF-002 token | E5 |
| Agency authors a token name that does not exist at runtime | M13, E11 |
| Required slot left empty → template's default rows charged instead | M1, M2 |

The last two are worse than a zero: they charge a value nobody authored.

## F. Corrections to the record — raised, not yet applied

Per the hub's hard rule, architectural facts need Sandeep's explicit
confirmation before the record is rewritten. These are code-verified but the
corresponding claims in `repos.md` / `impact-map.md` / `epic.md` are **left

1. **`nf-ndc-adapter-generic` is at specs 006–009**, not 004/005 —
   standardize-fee-discount, rule-evaluation-audit, subtype-scoped-aggregation
   and ticket-org-fee-discount are all implemented in that working tree. The
   impact map materially understates it.
2. **Python's ledger writes are not naive append.** Delete+recreate per chain
   level, gated on a multiset comparison that makes a same-answer re-eval a
   no-op, with the whole compute+write loop inside `transaction.atomic()` and
   `transaction.set_rollback(True)` on any level's BRE failure — the ledger is
   byte-identical after a failure. Real rollback semantics.
   (`content_rules.py:4606`, `:4616`, `:5305`, `:5259-5316`)
3. **Rust's money handling is stronger than recorded** — `BigDecimal` end to end
   via `RawValue` with no f64 round-trip, tested against `0.1+0.2`-class loss;
   currency-aware HalfUp rounding at every wire-write site; `cur_code` resolved
   per level and **erroring rather than defaulting** when absent; no
   `unwrap`/`expect` anywhere in the production BRE path. `epic.md` money item 1
   therefore applies to **Python only**.
4. **Batch position-correlation is mostly closed.** A length check exists and is
   tested (`evaluate.rs:153-161`, test `:885-897`) — a short or long response
   fails the level rather than zipping short. Chunking at 50 covers every pin and
   never truncates. The BRE returns a whole-request `400 BatchTooLarge` on 51+,
   never truncating, preserves request order, and isolates a per-item failure to
   that item while still writing its audit row. Only undetected **reordering**
   remains (E10).
5. **NF-001 / NF-002 "done and tested" in adapter-rs is true for OfferPrice and
   OrderQuote only**, not the OrderView surfaces — see E5.
6. **`reference` is not sent today.** `epic.md` item 3 records it as a
   requirement; E15 confirms no call site supplies it.
7. **Template republish is properly disclosed** — the publish-confirmation modal
   explicitly states that existing agency rulesets stay on the version they were
   built from and only new rulesets use the new one. Previously an open question;
   **not a gap.** (`RuleTemplateEditor.tsx:802`)
8. **P6 in `pending-confirmation.md` is factually answered.** For `bre_rule_set`
   the reachable lifecycle is `draft` → `published` → `invalidated`, with
   `invalidated` written on a publish race (`rule_set.rs:651`).
   `RuleStatus::Archived` is a **dead enum arm** — only a fallback display value
   for an unknown string, never written by any path (`graphql/common.rs:51`).
   What remains for Sandeep is the *intent* question, not the code question:
   was that lifecycle designed, or is it vestigial?
9. **Stronger guarantees than assumed, worth recording as such:** a published

   `template.rs:181-186`, `:303-311`), so template versions are effectively
